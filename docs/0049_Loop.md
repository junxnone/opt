## 常见循环变换一览

| 变换 | 做什么 | 主要收益 |
|---|---|---|
| Loop Unrolling（展开） | 把一次迭代的代码复制成多份，减少迭代次数 | 减少分支开销，提高指令级并行与寄存器重用 |
| Loop Pipelining（软件流水） | 把不同迭代的不同阶段重叠执行 | 填满流水线、消除等待空泡 |
| [Loop Fusion（合并）](0063_Loop_Fusion) | 把多个迭代空间相同的循环合并成一个 | 减少循环开销，提升数据重用 |
| Loop Fission/Distribution（分裂） | Fusion 的反操作，把一个大循环拆成多个 | 降低寄存器压力、让其中一部分能单独向量化/并行化 |
| Loop Interchange（交换） | 调换嵌套循环的层级顺序 | 让最内层按内存连续方向访问，提升 Cache 命中率 |
| Loop Tiling/Blocking（分块） | 把大迭代空间切成小块逐块处理 | 让每块工作集能放进 Cache，大幅减少容量性 Cache Miss |
| Loop Invariant Code Motion（外提） | 把循环内不随迭代变化的计算挪到循环外 | 避免重复计算 |
| Loop Peeling（剥离） | 把首/尾几次特殊的迭代单独拿出来 | 消除循环体内的边界条件判断 |
| Loop Vectorization（向量化） | 把标量循环改成 SIMD 指令批量处理 | 单指令处理多个数据，吞吐数倍提升 |

其中 Interchange 和 Tiling 本质上是通过改变访存顺序来优化 Cache 行为，具体例子见 [内存优化 - Data Use and Reuse](0037_Mem)。


## Loop Pipelining

软件流水（Software Pipelining）：循环体内一条指令往往要经过多个流水线阶段（取数/计算/写回等）才能完成，如果严格按顺序一次只处理一次迭代，很多阶段会处于空闲等待状态。软件流水把**不同迭代的不同阶段重叠起来**执行——当第 N 次迭代在做计算时，第 N+1 次迭代已经可以开始取数，从而填满流水线、消除因为等待上一步结果而产生的空泡（stall）。

- 和 Loop Unrolling 的区别：Unrolling 是把多次迭代的代码在循环体里物理展开、减少分支判断次数；Pipelining 是重新调度指令的执行顺序，让跨迭代的指令级并行（ILP）被利用起来，两者经常配合使用——先展开出多份迭代代码，再把这些代码的指令交错排布；
- 现代乱序执行（Out-of-Order Execution）CPU 本身在硬件层面也会做类似的事情（参见 [0003 性能优化 - Hardware Tech](0003_OPT)），但编译器/HLS 工具做的软件流水是在编译期就显式重排指令，对没有强乱序能力的硬件（如 FPGA HLS、部分嵌入式 DSP）尤其重要。

## Loop Unrolling
- 牺牲程序大小来加快程序执行速度的方法
- **优化的逻辑**
  - 减少循环分支指令执行的次数
  - 更多的**指令级并行**, 
  - 增加**寄存器重用**，提高**访存效率**
- 展开方式
  - 编译器自动循环展开(LLVM - `-funroll-loops`)
  - pragma 定义展开(`#pragma clang loop unroll(enable)`)
  - 手动展开
- 循环完全展开: 按迭代次数对循环展开
- 过度循环展开: 增加寄存器压力, 引起缓存区溢出
- 循环展开不能整除的尾循环处理

### 数据合法性
- 对数据依赖进行分析
- 数组的 `先读后写` / `先写后读`

循环优化的合法性几乎都归结到**数据依赖分析**，标准的三类依赖（以跨迭代为例）：

| 依赖类型 | 别名 | 含义 | 示例 |
|---|---|---|---|
| 流依赖（Flow / True Dependence） | RAW（写后读） | 先写后读，是真实的数据流动，**无法通过改名消除** | `a[i] = ...; ... = a[i-1];` |
| 反依赖（Anti Dependence） | WAR（读后写） | 先读后写，是"存储位置复用"造成的假依赖 | `... = a[i+1]; a[i] = ...;` |
| 输出依赖（Output Dependence） | WAW（写后写） | 两次都写同一位置，同样是假依赖 | `a[i] = x; a[i] = y;` |

反依赖和输出依赖属于**名字依赖（name dependence）**，可以通过换个临时变量/数组（重命名）来打破；而流依赖是真正的计算顺序约束，只能通过改算法（如把串行累加改成并行归约）来处理。编译器无法确定两个指针是否指向同一块内存（指针别名问题）时，会保守地假设存在依赖、放弃优化——这时可以用 `restrict` 关键字（C99）或 `#pragma ivdep` 显式告诉编译器"这里没有依赖"。

### pragma 实现循环展开
- `#pragma clang loop unroll(enable)` 
- `#pragma clang loop unroll(full)` : 完全循环展开(需要知道迭代次数)
- `#pragma clang loop unroll_count(8)` : 指定循环展开次数


```
accum = 0;
#pragma unroll N
for (size_t i=0; i<4; i++) {
  accum += data[i];
}
sum_out = accum;
```

## 怎么确认优化是否生效

不要只看代码改没改，要确认编译器实际生成了什么：

```bash
# GCC：输出详细的向量化/展开决策报告（包括"为什么没优化"）
gcc -O3 -fopt-info-vec-all -fopt-info-loop-all ...

# Clang/LLVM：输出优化 remark，说明某个循环被/未被向量化及原因
clang -O3 -Rpass=loop-vectorize -Rpass-missed=loop-vectorize \
      -Rpass-analysis=loop-vectorize ...

# Intel 编译器：生成优化报告
icx -qopt-report=3 ...
```

这些报告最有价值的部分是"**未优化的原因**"——常见的有 "loop not vectorized: unsafe dependent memory operations"（存在数据依赖，可能是指针别名导致的误判，试试 `restrict`）、"cost model indicates vectorization is not beneficial"（编译器认为不划算，可能是迭代次数太少或访存不连续）。

另外也可以直接看汇编（`-S` 或 `objdump -d`）确认：有没有出现 `vmulps`/`vaddps` 这类向量指令、循环体是否被复制成了多份（展开）。性能层面的验证则用 [Vtune Microarchitecture Exploration](0058_Tools_Vtune_AT_Microarchitecture) 看 Retiring/Core Bound 的变化，或用 [Intel Advisor](0008_Tools_Advisor) 直接看向量化报告和 Roofline 位置。

## 和其他循环优化技术的关系
- [循环合并 Loop Fusion](0063_Loop_Fusion)：把多个循环合并成一个，减少循环开销、增加数据重用，是和 Unrolling/Pipelining 不同维度的优化——Fusion 作用于"多个循环之间"，Unrolling/Pipelining 作用于"单个循环内部"；
- 循环顺序调整（Loop Ordering）/分块（Blocking）：提升数据局部性和 Cache 命中率，详见 [内存优化 - Data Use and Reuse](0037_Mem)。
