# 内存优化

- 两个基本原则
  - 最小化数据移动
  - 数据存储在离使用更近的地方
- 使用优化函数库
  - BLAS - `Basic Linear Algebra Subprograms`：标准化的线性代数接口（向量/矩阵乘加等），具体实现（如 Intel MKL、OpenBLAS）会针对目标 CPU 做汇编级/向量化优化，通常比手写循环快一个数量级以上
  - Intel MKL - `Math Kernel Library`：Intel 官方针对自家 CPU 深度优化的数学库（BLAS/LAPACK/FFT 等），能自动利用 AVX/AVX-512 等向量指令集
- 内存带宽：内存子系统单位时间能搬运的数据量上限，是很多计算密集型/访存密集型程序的硬件天花板——当程序的计算量相对访存量较低（Arithmetic Intensity 低，参见 [0003 Roofline Model](0003_OPT)）时，再怎么优化计算本身，性能也会被内存带宽卡死，必须靠减少总访存量、提高数据重用来突破
- False Sharing：多线程各自读写不同变量，却因为这些变量落在同一条 Cache Line 上而互相拖累，具体原理和修复方法见 [Memory Cacheline](0036_Mem_CacheLine)
- SoA vs. AoS

## Memory Arch
- **按访问速度排序:** Registers/L1/L2/L3/DRAM(Local Memory)/`Remote Memory`/`Swap space virtual memory`(Hard Disk/SSD)
- 层级之间延迟差距是数量级级别的，下面是业界常引用的一组近似延迟数字（不同硬件代际会有出入，但相对量级关系基本成立）：

| 存储层级 | 近似延迟 | 相对 L1 的倍数 |
|---|---|---|
| L1 Cache 引用 | ~1 ns | 1x |
| L2 Cache 引用 | ~4 ns | ~4x |
| L3 Cache 引用 | ~15-40 ns | ~15-40x |
| 主存（DRAM）随机访问 | ~100 ns | ~100x |
| 同数据中心内网络往返 | ~0.5 ms | ~50 万 x |
| SSD 随机读 | ~几十-100 μs | ~几万 x |
| 机械硬盘寻道 | ~几 ms | ~百万 x |

这组数字最直观的含义：**一次 DRAM 访问比一次 L1 Cache 命中慢约两个数量级**，这也是为什么"让数据尽量留在更靠近计算单元的层级"（本文开头的两个基本原则）能带来巨大的性能差异。

容量则是反过来的——越快的层级越小，这决定了做循环分块（blocking）时该怎么选 block size：

| 层级 | 典型容量（现代 Intel 服务器 CPU） | 共享范围 |
|---|---|---|
| 寄存器 | 每核几百字节 | 单核独占 |
| L1D Cache | 每核 32-48 KB | 单核（SMT 下两个逻辑核共享） |
| L2 Cache | 每核 1-2 MB | 单核 |
| L3 / LLC | 几十 MB | 整个 Socket 共享 |
| DRAM | 几十 GB - 数 TB | 整机（NUMA 下分属各 node） |

分块时的经验法则：让单个 block 的工作集能装进目标层级（通常是 L2），并且要留出余量给其他同时活跃的数据——注意 LLC 是 Socket 内所有核共享的，多线程跑起来时每个线程实际能用的 LLC 份额要除以线程数。

## Data Use and Reuse

### Loop Ordering

- **i/j/k ordering**
- Loop k 中将多个值融入一个值(reduction operation)不能有效利用 SIMD 的并行
- 点积方法

```
for (i=0;i<n; i++) 
   for (j = 0; j<n; j++) 
     for (k=0;k<n; k++) 
         A[i][j] += B[i][k]* C[k][j] ;  
```

![image](https://user-images.githubusercontent.com/2216970/141824321-c26b058c-1dd1-41f4-9933-8d9111667898.png)

- **i/k/j ordering**
- 改成如下循环顺序可以有效利用 SIMD 和寄存器
- saxpy/daxpy
- icx 在某些优化模式下会自动交换循环顺序

```
for (i=0;i<n; i++)
   for (k = 0; k<n; k++)
     for (j=0;j<n; j++)
       a[i][j] += b[i][k]* c[k][j] ;
```

![image](https://user-images.githubusercontent.com/2216970/141824461-394bfd15-1839-454e-aebe-ca11b3fec18b.png)

### Data Reuse

- 上述例子中, 当 n 比较大时, 中间循环读取到的 vectors 只能被使用一次
- submatrices/blocksize
- 选取适当的 blocksize, 使在内部三个循环中  block data 保存在 cache(Registers) 中
- 只有在大数据时在有明显提升

```
for (i = 0; i < n; i+=blockSize)
   for (k=0; k<n ; k+= blockSize)   
      for (j = 0 ; j < n; j+=blockSize)      
         for (iInner = i; iInner<j+blockSize; iInner++)     
            for (kInner = k ; kInner<k+blockSize; kInner++)
               for (jInner = j ; jInner<j+blockSize ; jInner++)
                 a[iInner,jInner] += b[iInner,kInner] *
                    c[kInner, jInner]
```

### 数据对齐
- 建议 64 byte 边界对齐
- icx 支持不改源码编译 `align:rec64byte`
- **为什么要对齐**：一次未对齐的访问可能横跨两条 Cache Line，CPU 需要发两次访存请求再把结果拼起来（对应 VTune 里的 Split Loads/Split Stores 指标）；而 SIMD 指令里部分对齐加载指令（如 `movaps`）在地址未对齐时会直接触发异常或退化到更慢的非对齐版本
- 常用的对齐手段：

```c
// C11 / C++11 起的标准写法
alignas(64) float a[1024];

// POSIX
float *p;
posix_memalign((void**)&p, 64, 1024 * sizeof(float));

// C11
float *p = aligned_alloc(64, 1024 * sizeof(float));

// GCC/Clang 扩展
float a[1024] __attribute__((aligned(64)));
```

- 仅仅分配时对齐还不够，还要让编译器**知道**它是对齐的，才能生成对齐版本的向量指令：

```c
// OpenMP 4.0+
#pragma omp simd aligned(a, b : 64)
for (int i = 0; i < n; i++) a[i] += b[i];

// Intel 编译器
__assume_aligned(a, 64);
```

### Array of Structure vs. Structure of Array

- SIMD 敏感, data 连续时 加载会更有效率
- SDLT - SIMD 数据布局模板


```
struct {
   uint r, g, b, w ; 
} MyAoS[N] ;
```

```
struct {
   uint r[N] ;
   uint g[N] ;
   uint b[N] ;
   uint w[N] ;
} MySoA ;
```
> SOA 更有效的加载到 SIMD 寄存器

-- | 
![image](https://user-images.githubusercontent.com/2216970/146131330-67bb74e1-7a41-4beb-8195-5fbef76d9aca.png)

**怎么选**：

| 访问模式 | 更优布局 | 原因 |
|---|---|---|
| 对所有元素的**同一个字段**做批量运算（如把所有像素的 r 分量 +1） | SoA | 同字段数据在内存里连续，一条 Cache Line 全是有用数据，可直接向量化加载 |
| 每次只处理**一个元素的全部字段**（如逐个物体做完整碰撞检测） | AoS | 一个对象的所有字段在同一条 Cache Line 里，一次加载就够 |
| 两种模式都有 | **AoSoA**（混合布局） | 外层按固定大小的块（通常和 SIMD 宽度对齐）组织成数组，块内用 SoA，兼顾两种访问模式 |

常见坑：很多代码默认用 AoS（因为面向对象的写法天然就是 AoS），但热点循环实际是按字段批量处理的——这时候 AoS 会导致每条 Cache Line 里只有 1/N 的数据有用，白白浪费带宽。


### 线程共享内存

- 多线程程序除了要考虑单线程的数据局部性，还要考虑**哪些内存是共享的、哪些是私有的**：
  - 频繁被多个线程读写的共享数据，应优先检查是否存在 [False Sharing](0036_Mem_CacheLine)；只读共享数据（如只读的查找表）本身不会有这个问题，可以放心共享；
  - 能拆分成每个线程私有的数据（如循环内的累加临时变量），应该拆分成私有变量、最后再合并结果，而不是让所有线程直接竞争同一块共享内存；
- 多路（NUMA）服务器上，"共享内存"还隐含着**访问延迟不均等**的问题：线程访问本地 NUMA 节点内存比访问远端 Socket 的内存延迟高出不少。常见做法是用 `numactl` 把线程和它要访问的内存绑定在同一个 NUMA 节点上，或者依赖操作系统默认的 "first-touch" 策略（内存页在哪个线程第一次写入时，就分配在该线程所在的 NUMA 节点上）；
- 以上这些线程间的数据共享/竞争问题，和 [并行计算](0023_PARA) 里的同步开销是两个不同但相关的视角——前者看的是"数据放在哪里"，后者看的是"线程之间怎么协调"。

## 数据预取（Prefetch）

预取是在数据真正被用到之前，提前把它搬进 Cache，用来掩盖访存延迟（参见 [0003 性能优化 - Hardware Tech](0003_OPT)）：

- **硬件预取**：CPU 自动识别规律的访问模式（最典型的是连续顺序访问、固定步长访问）并提前取数，不需要写代码；这也是为什么"按行顺序访问"比"随机/跨行访问"快很多——后者硬件预取器识别不出规律，完全帮不上忙；
- **软件预取**：访问模式不规律（如遍历链表、间接索引 `a[idx[i]]`）时硬件预取器失效，可以用 intrinsic 显式提示：

```c
// GCC/Clang 通用写法：第二个参数 0=读 1=写，第三个参数是时间局部性(0-3)
__builtin_prefetch(&a[i + PREFETCH_DISTANCE], 0, 3);

// x86 intrinsic
_mm_prefetch((const char*)&a[i + PREFETCH_DISTANCE], _MM_HINT_T0);
```

- 使用要点：预取距离（PREFETCH_DISTANCE）要恰好覆盖访存延迟——取太近，数据还没到就要用；取太远，数据可能已经被挤出 Cache。实践中需要实测调优，而且软件预取本身也占用指令发射槽和访存带宽，用错了反而更慢，**优先考虑通过改数据布局让硬件预取能生效**，而不是一上来就手写预取。

## 减少数据移动

对应开头的第一条基本原则"最小化数据移动"——下面这些手段的共同点是**让同一份数据不被反复搬运**：

- **传引用而非传值**：C++ 里大对象用 `const&` 传参，返回值依赖 RVO/move 语义（`std::move`）而不是深拷贝；
- **原地（in-place）操作**：能复用输出缓冲区就不要每次新建，尤其是循环内；
- **`mmap` 替代 read/write**：文件直接映射进地址空间，省掉内核缓冲区到用户缓冲区的那次拷贝；
- **零拷贝 I/O**：`sendfile`/`splice` 让数据不经过用户态；
- **DMA**：让外设直接读写内存，不占用 CPU 做搬运；
- **异构计算里的共享内存**：如 SYCL/oneAPI 的 USM（Unified Shared Memory，见 [DPC++ 架构](0015_PARA_DPCPP_Arch)），避免 Host 和 Device 之间显式的来回拷贝；
- **算子融合**：把连续的多个处理步骤合并成一趟，中间结果留在寄存器/Cache 里而不是写回内存再读出来——这和 [循环合并](0063_Loop_Fusion) 是同一个思路在不同层次上的体现。

## 内存占用优化

前面讨论的都是"访存速度"，但有时候要优化的是**内存占用本身**（容量受限、或者为了让工作集能装进 Cache）：

- 选用紧凑的数据类型（能用 `int32` 就不用 `int64`，能用 `fp16/bf16` 就不用 `fp32`）；
- 调整结构体成员顺序减少对齐填充（见 [Memory Cacheline](0036_Mem_CacheLine)）；
- 对象复用/对象池，避免反复分配释放（见 [Mem Allocator](0074_Mem_Allocator)）；
- 用 [Vtune Memory Consumption](0060_Tools_Vtune_AT_MC) 定位内存分配热点和潜在泄漏。

注意"省内存"和"访存快"有时是一致的（工作集变小 → Cache 命中率提升），有时是冲突的（比如为避免伪共享而做的 padding 会增加内存占用），需要具体权衡。

## 怎么定位内存瓶颈

遇到怀疑是访存导致的性能问题时，典型排查路径：

1. 先用 [Vtune Microarchitecture Exploration](0058_Tools_Vtune_AT_Microarchitecture) 确认 Memory Bound 占比是否偏高；
2. 偏高则转 [Vtune Memory Access](0059_Tools_Vtune_AT_MA)，细化到是哪一级 Cache/DRAM 的问题：
   - L1/L2/L3 Bound 高 → 数据局部性差，考虑循环分块、调整数据布局（本文 Data Use and Reuse 一节）；
   - DRAM Bound 高且带宽利用率接近峰值 → 已经打满内存带宽，必须减少**总访存量**（算法级优化、数据压缩/复用），单纯调整访问顺序没用；
   - 多线程集中访问同一小块内存 → 检查 [False Sharing](0036_Mem_CacheLine)；
   - NUMA 远端访问占比高 → 绑核绑内存。
3. 完整的排查分支图见 [Vtune Pipeline](0071_Tools_Vtune_Pipeline)。
