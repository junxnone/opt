# 循环合并
- **Loop Fusion - 循环合并** : 将具有相同迭代空间的循环合并成一个循环
- 减小迭代开销
- 增加数据重用，寄存器重用
- 减小并行化启动/同步开销
- 是 [Loop Optimization](0049_Loop) 系列里作用于"多个循环之间"的一种变换，和作用于"单个循环内部"的 Loop Unrolling/Pipelining 是不同维度，两者可以叠加使用

## 示例

```c
// 合并前：两个独立的循环，各自遍历一遍 n 个元素
for (i = 0; i < n; i++) {
    a[i] = b[i] + 1;
}
for (i = 0; i < n; i++) {
    c[i] = a[i] * 2;
}
```

```c
// 合并后：一次循环里做完两件事
for (i = 0; i < n; i++) {
    a[i] = b[i] + 1;
    c[i] = a[i] * 2;
}
```

合并后只需要一次循环控制开销（计数器自增、条件判断、跳转），而且 `a[i]` 刚写入就被马上读取，大概率还在寄存器或 L1 Cache 里，不需要再走一次内存。如果是并行循环（如 OpenMP `#pragma omp parallel for`），合并前需要两次线程启动/同步，合并后只需要一次。

## 合法性检查

前提条件：两个循环的**迭代空间必须相同**（循环次数、步长一致），否则要先做循环对齐/剥离（Loop Peeling）等变换，把迭代空间调成一致才能考虑合并。

- 不能违反原有依赖关系：如果循环 1 的某次迭代结果，被循环 2 的**更早**迭代依赖，合并后会打乱这个依赖的先后顺序，结果就错了
  - 例如上面的例子里，如果循环 2 写成 `c[i] = a[i+1] * 2`（依赖 `a` 的下一个元素），合并成一个循环后，`a[i+1]` 这时候还没被循环 1 算出来，直接合并就是错的

```c
// 不能合并的例子：fusion-preventing dependence
for (i = 0; i < n; i++) {
    a[i] = b[i] + 1;
}
for (i = 0; i < n; i++) {
    c[i] = a[i+1] * 2;     // 读的是 a 的下一个元素
}
// 合并后 a[i+1] 还没被算出来 —— 产生了一个"向后"的依赖（negative dependence distance），非法
```

- 不能产生新的依赖：两个循环各自独立时没有的依赖关系，合并后可能凭空出现，同样会破坏正确性
- 实现层面还有一些额外约束，比如 LLVM 的 Loop Fusion Pass 要求两个循环必须是相邻的、控制流等价的（同样的条件下都会执行），且目前会直接拒绝存在跨循环 def-use 链的情况

## 有利性检查
- 分离限制: 并行循环和串行循环合并，合并后的循环整体退化为串行，反而失去了其中一个循环本可以并行执行的收益，无收益甚至是负收益
- 阻止并行的依赖限制: 两个合并前都能独立并行的循环，合并后如果在循环体内产生了跨语句的依赖关系，会导致合并后的循环反而无法并行，同样得不偿失

- 寄存器压力：合并后循环体变大、同时活跃的变量变多，可能超出可用寄存器数量导致溢出（spill 到栈上），反而变慢
- 工作集大小：两个循环各自访问的数组合并后同时在循环内被访问，如果总工作集超过 Cache 容量，原本各自能放进 Cache 的数据现在互相驱逐，局部性反而变差
- 向量化冲突：如果合并后的循环体里混入了无法向量化的语句，可能导致整个循环都失去向量化机会

即 Loop Fusion 不是无脑合并越多越好——先过合法性检查确保语义不变，再过有利性检查确保合并确实带来收益（减少开销、提升数据局部性），而不是把原本可以并行的循环拖成串行。

> 值得一提的是，LLVM 当前的 Loop Fusion Pass 文档里明确说明，它的有利性检查目前**总是返回"有收益"**——这是为了测试覆盖率而刻意为之的占位实现，真正的代价模型启发式还在演进中。也就是说，即便是工业级编译器，"该不该合并"这个判断也远没有"能不能合并"那么成熟。

## 反向变换：Loop Fission / Distribution（循环分裂）

Fusion 的反操作——把一个大循环拆成多个小循环，在下列场景反而是优化：

```c
// 拆分前：循环体里混了一句无法向量化的语句，整个循环都没法向量化
for (i = 0; i < n; i++) {
    a[i] = b[i] * 2;          // 可向量化
    c[i] = complex_call(d[i]); // 有副作用的函数调用，阻止向量化
}
```

```c
// 拆分后：第一个循环可以独立向量化
for (i = 0; i < n; i++) a[i] = b[i] * 2;
for (i = 0; i < n; i++) c[i] = complex_call(d[i]);
```

适用场景：
- 循环体内一部分能向量化/并行化、另一部分不能，拆开让能优化的部分单独受益；
- 循环体过大导致寄存器压力高或指令 Cache 命中率差；
- 单次迭代涉及的数组太多，工作集超出 Cache 容量，拆开后每个循环的工作集更小。

所以 Fusion 和 Fission 并不是"一个对一个错"，而是要看具体瓶颈在哪——瓶颈是循环开销/数据重用就 Fusion，瓶颈是向量化受阻/寄存器压力/工作集过大就 Fission。
